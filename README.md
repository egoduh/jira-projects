# jira-projects

Локальный веб-сайт со списком проектов из **Jira Server/DC 8.13.20**
(`GET /rest/api/2/project`).

На **чистом JDK** — ни Maven/Gradle, ни зависимостей. Встроенный
`com.sun.net.httpserver` отдаёт страницу, а `/api/projects` проксирует сырой JSON
из Jira: парсит его уже браузер, поэтому JSON-библиотека в Java не нужна. Это же
снимает CORS и не светит токен в браузере.

Аутентификация — токен **Kantega SSO Enterprise**. Kantega выдаёт персональные токены
поверх Jira 8.13, у которой нет нативных PAT (они появились только в Jira 8.14).

По [документации Kantega](https://kantega-sso.atlassian.net/wiki/spaces/KSE/pages/28049409/API+Authentication)
токен передаётся **собственной схемой** `Authorization: ksso-token <токен>` (режим
`JIRA_AUTH_MODE=ksso`), либо как Basic (`-u <логин>:<токен>`). Обычный `Bearer` для
Kantega, как правило, **не** подходит — Jira не понимает схему и отвечает как анониму (пустой
список или 401).

## Запуск

Нужен только установленный `java` (проверено на Java 11 и 17). Секреты берутся из
файла `.env` рядом со скриптом либо из переменных окружения.

```bash
cp .env.example .env      # впиши JIRA_BASE_URL и JIRA_TOKEN
java JiraProjects.java    # Java 11+ запускает исходник без компиляции
# открой в браузере http://localhost:8000
```

Если Java 8 (нет запуска исходника напрямую) — скомпилируй один раз:

```bash
javac JiraProjects.java && java JiraProjects
```

Остановить — `Ctrl+C`.

### В VSCode

Запускать проще всего через терминал: **Terminal → New Terminal** →
`java JiraProjects.java`. Отладчик/расширения не нужны.

## Переменные окружения (или .env)

| Переменная       | По умолчанию | Назначение                                   |
|------------------|--------------|----------------------------------------------|
| `JIRA_BASE_URL`  | —            | URL инстанса без `/rest/...`                 |
| `JIRA_TOKEN`     | —            | Токен Kantega (bearer) или пароль (basic)    |
| `JIRA_AUTH_MODE` | `bearer`     | `ksso` (Kantega) / `basic` / `bearer`        |
| `JIRA_USERNAME`  | —            | Только для `basic`                           |
| `JIRA_AUTH_SCHEME` | —          | Своё имя схемы: `Authorization: <схема> <токен>` |
| `JIRA_CACERT`    | —            | Путь к корп. CA (PEM/CRT) — правильный TLS   |
| `JIRA_INSECURE`  | —            | `1` — вообще не проверять TLS                 |
| `JIRA_TIMEOUT`   | `30`         | Таймаут, сек                                 |
| `PORT`           | `8000`       | Порт локального сайта                        |

## TLS-сертификат Jira

Если Jira по HTTPS за корпоративным удостоверяющим центром, есть два варианта.

**Правильный — доверять корп-CA (проверка сертификата сохраняется):**

1. Выгрузи сертификат CA в файл. Из браузера: замок в адресной строке →
   сведения о сертификате → экспорт корневого/промежуточного CA в `.crt` (Base-64/PEM).
   Или у админов Jira попроси файл корпоративного CA.
2. В `.env`: `JIRA_CACERT=C:\certs\company-ca.crt`

**Быстрый — игнорировать проверку (последнее средство, для локального запуска):**

```
JIRA_INSECURE=1
```

Приоритет: `JIRA_INSECURE` (если задан) → иначе `JIRA_CACERT` → иначе только системные CA JDK.

Что на странице: таблица Ключ / Название / Лид / Тип, живой фильтр, сортировка по клику
на заголовок, ссылка на каждый проект, кнопка «Обновить».

Секреты через `.env`/окружение, в git не попадают.

## Пустой список `[]`

Ответ `200 []` почти всегда значит, что **токен не применился** и Jira ответила как
анонимному пользователю (ему не видно проектов), а не вернула `401`.

Проверь, кто ты для Jira — открой **http://localhost:8000/api/whoami**:

- Показывает твоего пользователя (`name`, `displayName`) → токен принят, `[]` это уже
  вопрос прав (нет Browse-доступа к проектам — к админам Jira).
- Возвращает ошибку `401` / аноним → токен не принят в текущем режиме. Переключись на
  Basic: в `.env` укажи `JIRA_AUTH_MODE=basic` и `JIRA_USERNAME=<логин>` (токен Kantega
  часто работает как пароль в Basic-auth). После правки `.env` перезапусти `java`.
